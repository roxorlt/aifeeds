Metrics 补数据策略诊断

回答你的疑问：「现在补数据策略是不是有问题，不应该只补高热的内容」

① 根因：14 天硬编码窗口

worker/src/enrich.ts:884 中 runRefreshMetrics 默认 lookbackDays = 14， cron 每 5 分钟跑一次但只看「published_at ≥ 14 天前」的推文， 超过 14 天的推文永远不再被刷。

② DB 数据印证

按时间分桶看缺 metrics 比例，14 天是个非常清晰的断崖：

< 1d 151 0 0% 在窗口内，持续刷

关键事实：缺 metrics 的 5,999 条推文 全部 emitted=1（已推送到 dashboard）。 它们入库时就因为某些原因（scraper DOM 抓取偶发失败 / 当时 syndication API 拉不到） 没拿到 metrics，进入 14 天滚动窗口期间没刷到，过了 14 天后再也回不来。

③ 你的疑问澄清

你说「不应该只补高热的内容」——其实不是按热度截断，是按时间截断。 但效果上很接近你的直觉：

  • 14 天内的推文，普遍互动量更大、热度更高（用户在意新内容）
  • 14 天外的推文，热度基本定型，scraper 也较少再抓到
  • 所以「只刷 14 天内」≈「只刷热门期内的推文」

这种策略对「滚动榜单 / 实时看板」是合理的，但对「资讯归档 / 长尾回溯」就不合理—— 历史推文一旦缺数据就永远缺。

④ 修复方案对比

方案 改动 优点 缺点
① 扩窗口 把 lookbackDays 从 14 改成 60 最小改动，1 行 每轮 candidates 多 4x，cron 节奏被拖；> 60d 仍然不补
② NULL 优先（推荐） 改 selectRefreshCandidates 的 WHERE/ORDER： NULL metrics 任何时间都进 candidates 且优先排前 存量自动消化；稳态后回归原节奏；不增 cron 槽 存量清完前，新推文 metrics 刷新会被略压制
③ 加独立 mode 新增 backfill-missing-metrics，独立 cron 槽 完全解耦 需要新 mode + 配置开关，~50 行代码
④ on-demand 兜底 drawer 打开时按需 fetch（问题 1 已规划） 不浪费 cron 列表里仍然 —；不开 drawer 不补

⑤ 我的建议：方案 ② + ④

  1. SQL 改动：让 NULL metrics 在任何时间窗口都能进 candidates，并优先排前 
    WHERE source_type = 'x_list'
  AND is_relevant = 1
  AND (
    metrics IS NULL OR metrics = '{}'    -- 缺数据：永远是 candidate
    OR published_at >= ?                  -- 或：14 天内（保持原逻辑）
  )
ORDER BY
  CASE WHEN metrics IS NULL OR metrics = '{}' THEN 0 ELSE 1 END,  -- NULL 先
  published_at DESC
LIMIT ?
  2. 临时加速：把 cron limit 从 20 提到 100，5,999 / 100 ≈ 5 小时清完存量 （5 min × 60 轮）；或者保留 limit=20，25 小时自然清完。
  3. on-demand 兜底：问题 1 的 drawer 打开时 fetch，覆盖 (a) 还没轮到 cron 刷的、(b) 未来再发生 scraper 偶发失败导致 NULL 的
  4. 稳态校验：方案上线 24h 后看 DB WHERE metrics IS NULL 的总数应当 → 接近 0
