1.三个环境是干嘛的

ai-feeds 总共 3 套环境，目的不重叠：

环境谁在用能写吗挂了影响
prod 真实用户能（用户登录、订阅） 所有人看不到内容 / 登不上 → 紧急
staging 你测试新功能用能（不污染 prod 数据） 影响 0 — 只有你访问
dev 你本地写代码能（默认连 staging） 影响 0 — 只有你电脑
一句话原则：写代码在 dev，测改动在 staging，给用户用是 prod。任何写操作（登录、注册、发短信）都先在 staging 跑一遍，再合 main 部署 prod。

2.架构图

┌─────────── PROD（用户访问） ───────────┐ ┌────── STAGING（你测试） ──────┐ │ │ │ │ │ ai-feeds.com │ │ staging.ai-feeds.com │ │ ↓ │ │ ↓ │ │ api.ai-feeds.com │ │ staging-api.ai-feeds.com │ │ ↓ │ │ ↓ │ │ Worker: xlist-api │ │ Worker: xlist-api-staging │ │ ├─ D1: xlist ← 真用户数据│ │ ├─ D1: xlist-staging │ │ ├─ KV: AUTH_KV │ │ ├─ KV: AUTH_KV_STAGING │ │ └─ R2: xlist-readme-assets │ │ └─ R2: xlist-readme-stg │ │ │ │ │ │ Cron: 5min 抓取/enrich 全开 │ │ Cron: 全关（手动触发） │ │ SMS: 真腾讯云（用户收真短信） │ │ SMS: PushDeer 推 admin │ └────────────────────────────────────────┘ └──────────────────────────────┘ ┌────── LOCAL DEV（你的 macbook） ─────┐ │ │ │ localhost:5173 (vite dev server) │ │ ↓ vite proxy /api/* │ │ 默认: staging-api.ai-feeds.com │ │ （想连 prod？VITE_API_PROXY 覆盖） │ └──────────────────────────────────────┘

每条线代表「请求从哪儿打到哪儿」。prod 跟 staging 完全不共享数据库 / 缓存 / 文件存储，独立资源 ID。

3.日常 workflow（按场景）

场景 A：改一个 dashboard 按钮颜色

流程：dev → 直接合 prod（纯视觉，跳过 staging）

在 worktree 里改组件，npm run dev 在浏览器看效果
改对了 → commit 到 main
cd dashboard && npm run build && npx wrangler pages deploy dist --project-name=xlist-dashboard --branch=main
ai-feeds.com 强刷验证

场景 B：改 worker 加新 API endpoint

流程：dev → staging → prod（任何 worker 改动都过 staging）

开 feature branch + worktree
改 worker/src/，加新 endpoint
本地 dashboard npm run dev 调 staging worker（默认）—— 等 staging 部署后再测
cd worker && npx wrangler deploy --env staging
在 staging 域名下测新 endpoint：curl https://staging-api.ai-feeds.com/api/xxx
OK → 合 main → npx wrangler deploy（不带 env 默认 prod）
prod 验收

场景 C：D1 schema 变更（加列、新表）

流程：staging migration → 验证 → prod migration → 部署 worker

写 worker/migrations/0NN-xxx.sql
staging 先跑：npx wrangler d1 migrations apply xlist-staging --env staging --remote
staging worker 部署 + 跑测试 endpoint，确认 schema 变更不破坏现有数据
prod 跑 migration：npx wrangler d1 migrations apply xlist --remote
prod worker 部署
禁止：直接 wrangler d1 execute --remote --command="ALTER TABLE..." 改 prod。一定要走 migration 文件，方便回滚。

场景 D：测试登录 / SMS 流程

流程：staging（永远不在 prod 测登录）

staging 的 SMS_PROVIDER=pushdeer，验证码会推到管理员手机的 PushDeer，不发真短信
本地 npm run dev 默认连 staging，登录流程跑通
登录态、注销、风控都在 staging 演练
不要在 prod 测登录：会消耗每日 200 条 SMS cap、把你手机号写进 prod 风控表，被锁后还得用 admin panel 解。

场景 E：dashboard + worker 同时改（最容易翻车）

流程：必须同时部署 staging 验证 → 同时合 main → 同时部署 prod

同一 feature branch 改 worker + dashboard
worker 先 staging：wrangler deploy --env staging
dashboard 后 staging：npm run deploy:staging
在 staging.ai-feeds.com 验真
合 main → 同一会话部署 prod 两边
反面教材：PR3 第一次部署，dashboard 升级了 fetch credentials: 'include'，但 worker CORS 没跟上 Allow-Credentials: true，prod 全站 fetch 失败。如果当时 staging 同步部署，5 分钟内就能发现。

4.数据怎么管

数据类型prod 策略staging 策略
Items（推文/repo） cron 自动抓取/enrich cron 关，从 prod export 一次种子
Users / Sessions 真用户数据 schema-only + 你自己手动注册的测试账号
Events（埋点） 所有用户行为 只有你测试时产生的；不污染 prod 漏斗
SMS log 真发短信记录 PushDeer 推送记录

staging 数据初始化

# 1. 从 prod export schema（不带数据，避免泄露真用户隐私）
cd worker
npx wrangler d1 export xlist --remote --output=schema.sql --no-data

# 2. 灌进 staging
npx wrangler d1 execute xlist-staging --env staging --remote --file=schema.sql

# 3. 手动塞几条测试数据（自己在 staging.ai-feeds.com 注册一次就行）

# 4. 想要内容数据？跑一次 GitHub trending fetch 即可
curl -X POST -H "Authorization: Bearer $INGEST_TOKEN_STAGING" \
  https://staging-api.ai-feeds.com/api/enrich/run?mode=github-fetch

6.备份 & 恢复

本地 launchd 周备份（已规划，PR6 落地）

# ~/Library/LaunchAgents/com.aifeeds.d1-backup.plist
# 每周日 02:00 BJT 触发
cd ~/brain/30-projects/xlist-scraper/worker
DATE=$(date +%Y%m%d)
npx wrangler d1 export xlist --remote --output=/tmp/xlist-$DATE.sql
gzip /tmp/xlist-$DATE.sql

# 上传到 staging R2 bucket（prod / staging 共用 R2 配额，免费）
npx wrangler r2 object put \
  xlist-readme-assets-staging/backups/xlist-$DATE.sql.gz \
  --file=/tmp/xlist-$DATE.sql.gz

rm /tmp/xlist-$DATE.sql.gz

# 保留最近 12 周（旧的 R2 lifecycle 自动删，或脚本扫）

恢复

# 1. 拉备份
npx wrangler r2 object get \
  xlist-readme-assets-staging/backups/xlist-20260503.sql.gz \
  --file=/tmp/restore.sql.gz
gunzip /tmp/restore.sql.gz

# 2. 灌进新 D1（不要直接覆盖 prod！）
npx wrangler d1 create xlist-restore
npx wrangler d1 execute xlist-restore --remote --file=/tmp/restore.sql

# 3. 验证 xlist-restore 数据没问题

# 4. 切换：改 wrangler.toml 的 database_id 指向新库 + 部署

7.应急 playbook

🔥 prod 全站 fetch 挂了（CORS / 500） 
# 1. 看 worker 日志
cd worker && npx wrangler tail

# 2. 是不是 dashboard 跟 worker 不匹配？看最近一次部署
npx wrangler deployments list

# 3. 回滚 worker（用上一个 version ID）
npx wrangler rollback <version-id>

# 4. dashboard 也回滚（CF Pages dashboard → Deployments → 历史里点 Rollback）

# 5. 找到根因再部署
🔥 prod D1 数据被误改 / 删 
# 立刻检查最近备份
npx wrangler r2 object list xlist-readme-assets-staging --prefix=backups/

# 拉最新一份恢复（见第 6 节）
# 切换到 xlist-restore 验证 → 改 wrangler.toml 切回
🔥 admin secret 泄露 
cd worker
echo "新强密码" | npx wrangler secret put ADMIN_PASS

# 部署即刻生效，无需重新 deploy（secret 是 hot reload 的）
# 但保险起见跑一次 wrangler deploy
🔥 SMS 风控锁住 / 用量爆了 
# 看用量
curl -u "***ADMIN-CREDS-REDACTED***" https://api.ai-feeds.com/api/admin/daily-cap

# 临时关闭 SMS（设 SMS_DAILY_CAP=0 是 kill switch）
echo "0" | npx wrangler secret put SMS_DAILY_CAP

# 解锁某号
curl -u "***ADMIN-CREDS-REDACTED***" -X POST -H "Content-Type: application/json" \
  https://api.ai-feeds.com/api/admin/unlock-sms \
  -d '{"phone":"166xxxxxxxx"}'

# 或直接打开 admin panel：https://api.ai-feeds.com/admin
🔥 worker / dashboard 一个改对、一个忘了部署 
# 看当前部署状态
npx wrangler deployments list  # worker
npx wrangler pages deployment list --project-name=xlist-dashboard  # dashboard

# 看 source 字段对应的 commit hash 是不是 main HEAD
git log --oneline -1

# 不一致的那边重新部署

8.Claude Code 帮你做

下面这些事你不用记命令，跟 Claude Code 说一句中文就行：

说什么Claude 帮你跑
「部署 dashboard 到 prod」build + wrangler pages deploy + 验证
「部署 worker 到 staging」wrangler deploy --env staging
「备份 prod D1」wrangler d1 export + 上传 R2
「把 prod schema 同步到 staging」export schema-only + execute on staging
「prod 在挂吗？」curl + wrangler tail + 看最近部署 hash
「16619811550 命中风控解一下」调 admin endpoint 或直接 d1 execute UPDATE
「合并 main + 部署」merge --no-ff + 双端 deploy + 验真
但是：涉及 prod 写操作（部署、删数据、改 schema、merge）Claude 都会先跟你确认再动手。你可以授权一次性自动跑（"直接做完不用问"），但默认是 ask-first。

9.命令速查

部署

# Worker
cd worker
npx wrangler deploy                  # → prod
npx wrangler deploy --env staging    # → staging

# Dashboard (CF Pages)
cd dashboard
npm run build
npx wrangler pages deploy dist --project-name=xlist-dashboard --branch=main          # prod
npx wrangler pages deploy dist --project-name=xlist-dashboard-staging                # staging

# 看部署历史
npx wrangler deployments list                          # worker
npx wrangler pages deployment list --project-name=...  # dashboard

# 回滚
npx wrangler rollback <version-id>

D1

# 查 schema
npx wrangler d1 execute xlist --remote --command="SELECT name FROM sqlite_master WHERE type='table'"

# 跑临时查询（生产慎用）
npx wrangler d1 execute xlist --remote --command="SELECT COUNT(*) FROM items"

# 应用 migration
npx wrangler d1 migrations apply xlist --remote
npx wrangler d1 migrations apply xlist-staging --env staging --remote

# 导出
npx wrangler d1 export xlist --remote --output=backup.sql
npx wrangler d1 export xlist --remote --no-data --output=schema.sql  # 仅 schema

Secret

echo "value" | npx wrangler secret put NAME              # prod
echo "value" | npx wrangler secret put NAME --env staging # staging
npx wrangler secret list
