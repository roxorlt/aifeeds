## Problem Statement

xList scraper 已稳定运行 14+ 天（launchd 每 30 分钟触发，17K+ 推文入库）。Week 1 的「稳定基础」目标达成。

现在需要把数据从本地 SQLite 搬到云端，让用户通过 URL 直接访问，同时开始接入第二个数据源（YouTube）。用户要求「抓完即可见」的实时性，不接受 6 小时的静态导出延迟。

这推翻了 04-09 设计文档的「静态 JSON + Vercel」方案，改为 Cloudflare D1 + Workers + Pages 全栈。

## Demand Evidence

（继承自 04-09 设计文档，无变化）

三级目标用户：手动翻墙浏览 X 的人、被墙挡住靠搬运工的人、在微信/小红书看三手信息的人。团队成员和社区朋友已在使用 markdown 导出。竞争壁垒是多源聚合，不是单源速度。

## Constraints

1. 抓取必须留在本地 MacBook（翻墙需求，X/YouTube API 需梯子）
2. Solo developer，选型必须运维量极低
3. 现有 Python 抓取管道不变，只加云端推送
4. 本地 SQLite 保留作为备份和离线兜底

## Premises

1. ~~静态 JSON 导出够用~~ → **不够**。用户要实时。需要 scraper 写完即可查询的云端存储。
2. 「实时」= scraper 完成后 Dashboard 立即可见。scraper 每 30 分钟跑一次，Dashboard 每 30 秒轮询。用户感知延迟 ≈ 30 分钟（scraper 间隔），轮询本身不是瓶颈。
3. Cloudflare D1（边缘 SQLite）是最优选型：SQLite 兼容（现有 schema 迁移几乎零成本）、免费层充足（5GB DB + 10 万写入/天 + 500 万读取/天）、全栈一体（D1 + Workers + Pages）。
4. React + shadcn/ui 是 Dashboard 最优选型：AI 辅助编码效果最好、组件生态最大、多源卡片组件化开发方便。
5. YouTube Data API v3 是第二个数据源（非 browser-use 抓取）。API 访问需梯子，运行在本地。

## Architecture

```
本地 MacBook（需梯子）                Cloudflare（全球边缘）
┌────────────────────────┐         ┌─────────────────────────────┐
│                        │         │                             │
│  X List Scraper        │──POST──▶│  Worker: /api/ingest        │
│  (browser-use, 30min)  │         │    ↓                        │
│                        │         │  D1 Database (SQLite edge)  │
│  YouTube Scraper       │──POST──▶│    ↑                        │
│  (API v3, 6hr)         │         │  Worker: /api/items         │
│                        │         │    ↑                        │
│  (future scrapers)     │──POST──▶│  Pages: React Dashboard     │
│                        │         │    (polls /api/items 30s)   │
│  Local SQLite (backup) │         │                             │
│  launchd scheduler     │         └─────────────────────────────┘
└────────────────────────┘
```

数据流：
1. launchd 触发 scraper → 抓取 + LLM 过滤 + 翻译（全部在本地完成）
2. scraper 写入本地 SQLite（保持现有逻辑不变）
3. scraper 额外调用 `POST /api/ingest` 将处理好的数据推到 D1
4. Dashboard 每 30 秒 `GET /api/items` 查询 D1 最新数据
5. 离线兜底：如果 Worker 不可达，数据暂存本地，下次运行时重试

## D1 Database Schema

统一内容模型。从现有 `tweets` 表抽象为通用 `items` 表：

```sql
-- 统一内容表
CREATE TABLE items (
  id TEXT PRIMARY KEY,              -- "{source_type}:{source_id}" e.g. "x:1234567890"
  source_type TEXT NOT NULL,        -- x_list | youtube | podcast | product_hunt | github
  source_id TEXT NOT NULL,          -- 平台原始 ID（tweet_id, video_id, etc.）
  source_ref TEXT,                  -- 来源容器（list_id, channel_id, feed_url）
  title TEXT,                       -- 标题（推文为 NULL，视频/文章有标题）
  content TEXT,                     -- 原文正文/描述（YouTube 视频描述可能为空）
  content_translated TEXT,          -- 中文翻译（原文已是中文则为 NULL）
  author TEXT,                      -- 作者/频道名
  handle TEXT,                      -- @handle（适用时）
  url TEXT,                         -- 原始链接
  media TEXT,                       -- JSON: [{type, url, width, height, alt}]
  metrics TEXT,                     -- JSON: {views, likes, replies, retweets, ...}
  published_at TEXT,                -- ISO 8601 内容发布时间
  scraped_at TEXT NOT NULL,         -- ISO 8601 入库时间
  is_relevant INTEGER DEFAULT 1,   -- 1=AI相关, 0=不相关, NULL=未分类
  matched_by TEXT,                  -- keyword | llm | NULL
  lang TEXT,                        -- 原始语言 en/zh/...
  extra TEXT,                       -- JSON: 源类型特有字段（hashtags, duration, stars...）
  -- 注：id = "{source_type}:{source_id}" 由 Worker 生成
  UNIQUE(source_type, source_id)    -- 防止 id 生成 bug 导致重复插入
);

-- 数据源配置表
CREATE TABLE sources (
  id TEXT PRIMARY KEY,              -- "{source_type}:{source_ref}"
  source_type TEXT NOT NULL,        -- x_list | youtube | podcast | ...
  source_ref TEXT NOT NULL,         -- list_id, channel_id, feed_url
  name TEXT,                        -- 显示名称
  topic TEXT,                       -- AI 主题描述（用于 LLM 过滤）
  cursor TEXT,                      -- 上次处理到的位置标记
  last_success_at TEXT,             -- 上次成功抓取时间
  config TEXT,                      -- JSON: {frequency, keywords, ...}
  UNIQUE(source_type, source_ref)
);

-- 运行统计表
CREATE TABLE run_stats (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  source_id TEXT NOT NULL,          -- 关联 sources.id
  run_at TEXT NOT NULL,
  new_count INTEGER,
  relevant_count INTEGER,
  stop_reason TEXT,
  duration_s INTEGER
);

-- 索引
CREATE INDEX idx_items_scraped ON items(scraped_at DESC);
CREATE INDEX idx_items_source_scraped ON items(source_type, scraped_at DESC);
CREATE INDEX idx_items_relevant ON items(is_relevant, scraped_at DESC);
CREATE INDEX idx_items_published ON items(published_at DESC);
```

## Worker API Design

Worker 托管在 Cloudflare Workers，路径前缀 `/api`。

### POST /api/ingest （写入，需认证）

```
Headers:
  Authorization: Bearer <INGEST_TOKEN>
  Content-Type: application/json

Body:
{
  "source": {
    "id": "x_list:1643236611378008066",
    "cursor": "1234567890",
    "last_success_at": "2026-04-15T12:00:00Z"
  },
  "items": [
    {
      "source_type": "x_list",
      "source_id": "1234567890",
      "source_ref": "1643236611378008066",
      "content": "...",
      "content_translated": "...",
      "author": "Sam Altman",
      "handle": "sama",
      "media": [...],
      "metrics": {...},
      "published_at": "2026-04-15T10:00:00Z",
      "scraped_at": "2026-04-15T12:00:00Z",
      "is_relevant": 1,
      "matched_by": "keyword",
      "lang": "en",
      "extra": {...}
    }
  ]
}

Response 200:
{
  "inserted": 5,
  "updated": 2,
  "errors": []
}
```

逻辑：
- **UPSERT**（`INSERT ... ON CONFLICT(source_type, source_id) DO UPDATE SET ...`），只更新 payload 中包含的列，不破坏未传入的列
- Worker 服务端生成 `id = "{source_type}:{source_id}"`，客户端不传 id
- 更新 source cursor 和 last_success_at
- **D1 batch 限制**：D1 Workers binding 每批最多 100 条 bound statements。Worker 内部将 payload 按 100 条分片，逐批写入同一事务。客户端单次 POST 最多 500 条。
- **部分失败处理**：每个 item 独立 UPSERT，失败的 item 记入 response `errors` 数组（含 source_id + 错误原因），成功的不受影响。非 all-or-nothing。


### 认证模型

- **写操作**（POST /api/ingest）：Bearer token，存在 Worker 环境变量 `INGEST_TOKEN`
- **读操作**（GET /api/*）：公开，无认证
- **CORS**：Worker 需配置 `Access-Control-Allow-Origin` 为 Pages 域名（如 `https://xlist.pages.dev`）和 `http://localhost:5173`（Vite dev server）。需处理 preflight `OPTIONS` 请求。
- **Rate limiting**：Cloudflare 免费层不含 Rate Limiting 产品。MVP 阶段流量低，不需要。如有滥用，可通过 Worker 代码实现简单的 IP 限流（内存计数器），或升级 Cloudflare WAF。

### 轮询策略

```typescript
// useItemsFeed hook
const POLL_INTERVAL = 30_000; // 30 秒

function useItemsFeed(sourceFilter?: string) {
  const [items, setItems] = useState<Item[]>([]);
  const [pendingItems, setPendingItems] = useState<Item[]>([]);
  const lastScrapedAt = useRef<string>();

  // 初始加载：获取最近 7 天数据
  useEffect(() => {
    fetch(`/api/items?limit=50&source_type=${sourceFilter || ''}`)
      .then(r => r.json())
      .then(data => {
        setItems(data.items);
        if (data.items.length > 0) {
          lastScrapedAt.current = data.items[0].scraped_at;
        }
      });
  }, [sourceFilter]);

  // 轮询：只获取新数据，不自动插入
  useEffect(() => {
    if (!lastScrapedAt.current) return;
    const poll = async () => {
      const res = await fetch(
        `/api/items?since=${lastScrapedAt.current}&source_type=${sourceFilter || ''}`
      );
      const data = await res.json();
      if (data.items.length > 0) {
        setPendingItems(prev => [...data.items, ...prev]);
        lastScrapedAt.current = data.items[0].scraped_at;
      }
    };
    const id = setInterval(poll, POLL_INTERVAL);
    return () => clearInterval(id);
  }, [sourceFilter]);

  // 用户点击「N 条新内容」时调用
  const showPending = () => {
    setItems(prev => [...pendingItems, ...prev]);
    setPendingItems([]);
  };

  return { items, pendingCount: pendingItems.length, showPending };
}
```

用户点击「N 条新内容」时，将新数据 prepend 到 feed 顶部。避免自动插入导致正在阅读的内容跳动。

## YouTube Scraper Design

### 技术方案

- Python 脚本，与 xlist scraper 同级放在 `~/.claude/skills/xlist-scraper/scripts/`
- YouTube Data API v3（REST，不需要 browser-use）
- API Key 认证（不需要 OAuth，只读公开数据）
- 免费配额：10,000 units/day（search.list = 100 units，足够 100 次调用/天）

### 抓取流程

```
1. 从 sources 表（或本地配置）读取已订阅的 YouTube channel IDs
2. 对每个 channel：
   a. 调用 playlistItems.list（频道上传播放列表）获取最新视频
   b. 对比本地 cursor（上次处理到的 video_id），只处理新视频
   c. 调用 videos.list 获取详细信息（description, metrics, duration）
3. LLM 过滤：复用 DeepSeek 的 AI 相关性判断
4. 翻译：复用现有翻译管道（标题 + 描述）
5. 写入本地 SQLite + POST 到 Worker /api/ingest
6. 更新 source cursor
```

### API 调用量预估

假设监控 20 个频道，每天每频道 ~2 个新视频：
- playlistItems.list: 20 channels × 3 units = 60 units
- videos.list: 40 videos × 1 unit = 40 units
- 单次运行 ~100 units
- 每天 4 次（每 6 小时）= ~400 units/day，远低于 10,000 上限

## Scraper Integration（现有 xlist scraper 改造）

改动最小化。现有流程不变，只在 `output.py` 的 `save_to_db()` **之后** 加一个云端推送步骤。

**调用时序**：scraper dict → `save_to_db()` 写入本地 SQLite → 从 DB 读出行 → `push_to_cloud()` 推到云端。`tweet_to_item()` 接收的是 **DB 行**（字段名为 tweet_id, text, media 等 DB 列名），不是 scraper dict（字段名为 author_name, content, attachments）。

### output.py 新增函数

```python
import requests
import os

WORKER_URL = os.getenv("XLIST_WORKER_URL", "https://xlist-api.your-domain.workers.dev")
INGEST_TOKEN = os.getenv("XLIST_INGEST_TOKEN")

def push_to_cloud(items: list[dict], source_info: dict) -> dict:
    """将处理好的数据推送到 Cloudflare Worker"""
    if not INGEST_TOKEN:
        return {"skipped": True, "reason": "no INGEST_TOKEN configured"}
    
    # 转换为 items 表格式
    cloud_items = [tweet_to_item(item) for item in items]
    
    try:
        resp = requests.post(
            f"{WORKER_URL}/api/ingest",
            json={"items": cloud_items, "source": source_info},
            headers={"Authorization": f"Bearer {INGEST_TOKEN}"},
            timeout=30
        )
        resp.raise_for_status()
        return resp.json()
    except Exception as e:
        # 离线兜底：记录失败，下次重试
        save_pending_push(cloud_items, source_info)
        return {"error": str(e)}

def tweet_to_item(tweet: dict) -> dict:
    """tweets 表格式 → items 表格式"""
    return {
        "source_type": "x_list",
        "source_id": tweet["tweet_id"],
        "source_ref": tweet["list_id"],
        "title": None,
        "content": tweet["text"],
        "content_translated": tweet.get("translated"),
        "author": tweet.get("author"),
        "handle": tweet.get("handle"),
        "url": f"https://x.com/{tweet.get('handle', '_')}/status/{tweet['tweet_id']}",
        "media": tweet.get("media"),
        "metrics": tweet.get("metrics"),
        "published_at": tweet.get("created_at"),
        "scraped_at": tweet.get("scraped_at"),
        "is_relevant": tweet.get("is_ai"),
        "matched_by": tweet.get("matched_by"),
        "lang": tweet.get("lang"),
        "extra": json.dumps({
            k: tweet.get(k) for k in 
            ["hashtags", "urls", "author_id", "profile_image_url", 
             "is_verified", "reply_to_id", "quote_of_id", "thread_root_id", "ocr_text"]
            if tweet.get(k) is not None
        })
    }
```

### 离线兜底

Worker 不可达时，数据暂存到 `data/pending_push.jsonl`，每行一个 JSON 对象。

重试逻辑：
1. 每次 scraper 运行时，先检查 `pending_push.jsonl` 是否存在且非空
2. 有则按行读取，分批 POST 到 Worker（每批 200 条）
3. 成功的行删除，失败的保留
4. **去重**：Worker 端使用 UPSERT（ON CONFLICT DO UPDATE），即使同一条数据重复推送也不会产生脏数据
5. **文件上限**：如果 pending 文件超过 10,000 行（约 5MB），truncate 最老的条目并 log 告警
6. **最大重试**：不限次数。只要 Worker 恢复，积压数据最终会推送完。本地 SQLite 始终有完整数据。

### push_to_cloud 对 scraper 运行时间的影响

现有 scraper 单次运行约 1-5 分钟（browser-use 抓取 + LLM 过滤 + 翻译）。`push_to_cloud()` 增加的网络 I/O：
- 正常情况：每批 200 条，POST 耗时 ~1-2 秒，总增加 ~5 秒
- 超时/重试：`timeout=30s`，最多增加 30 秒
- 结论：不会导致 30 分钟 launchd 间隔重叠。现有 `cron.sh` 的 PID 锁机制仍然有效。
