当前 7 类已知问题

这些是前端不停发现要打补丁的根源。同一个底层原因（流程没设计完整 + 没数据闭环），每一项都在影响 feed 阅读体验。

编号 现象 原因 影响范围
1 正文末尾 …，只看到 140 字 入库时拿的是列表页截断版，没补全 入库阶段所有英文长推
2 转发的推文，显示的是转发者，不是原作者 第 4c 步「回填转发原推」漏写了 所有转发类型推文
3 中文翻译还是老的截断版 补全正文后没清旧翻译，翻译永远停在第一版 所有被补全过正文的英文推文
4 引用别人推文，只看到自己一句话，看不到被引用的内容 第 4a 步「回填引用原推」失败没重试 / 老数据没跑过 部分引用类型推文
5 转发 / 引用推文里的视频不能播 拿回来的是封面图，不是视频播放地址 所有转发 / 引用里带视频的
6 英文推文长时间没翻译 翻译用的是另一套定时任务随机抽选，跑不赢新增量 部分英文推文翻译滞后几小时到几天
7 主推一句话「+1」+ 引用原推是 OpenAI 新闻 → 被误判不相关丢弃 相关性判定在关联数据回填之前，只看主推就判 所有「评论性引用 / 回复」的相关推文

共同原因：之前的流程是「先做一部分上线，剩下的边发现边补」的增量模式，没有一个统一的「数据完整」标准。前端拿到的有时是半成品，所以一直在打补丁。

第 6 步「相关性判定 + 翻译」验收标准

改代码前先把验收标准定下来。开工后测试阶段对照这里逐项验，不达标不上线。

① 输出 JSON 结构正确 必填字段：is_relevant（值 0 或 1）、reason（≥ 5 个字符）
条件必填：is_relevant=1 且对应原文非空时，对应翻译字段必填。
字段名约定：content_zh / quote_of_zh / reply_of_zh / retweet_of_zh / link_card_title_zh / link_card_desc_zh
② 字段完整性 用 DeepSeek JSON Mode（强制 schema），返回缺字段或类型不对一律视为失败。
验收方法：跑 100 条样本，字段完整率 ≥ 99%。
③ 翻译质量 · 中文流畅，无明显机翻 / 英文残留
· 保留 URL / @mention / hashtag 原文不翻
· 翻译长度 0.5 到 1.5 倍原文（防截断或胡乱扩展）
验收方法：随机抽 20 条人工评，≥ 16 条可接受
④ 相关性判定准确率 拿已标注的 100 条历史样本对比旧逻辑 vs 新合并调用，判定一致率 ≥ 90%。
额外：用户翻 feed 时连续 50 条没明显不相关混入。
⑤ 响应时间 单次调用 P95 < 5 秒（v4-flash 标准）
验收方法：连续跑 200 次取分布，P95 不超标
⑥ 失败率与兜底 整体失败率（含超时 / JSON 解析失败）< 1%
失败时回落到「分开调用」老逻辑（判定一次 + 翻译多次），不阻塞流程
验收方法：模拟 50 次故意制造长 prompt 触发超时，回落机制 100% 触发
⑦ 成本下降 单条推文大模型调用次数从原来的 5 到 6 次 → 1 次
月度账单与旧逻辑对比下降 ≥ 70%
验收方法：上线 7 天后对比成本数据
⑧ 边缘 case 覆盖 7 种组合每种至少 3 条样本必须通过：
· 主推一字（"+1"）+ 引用是 AI 内容
· 长推 25k 字符
· 含 emoji / 全 emoji
· 多语言混合（英 + 中 + 日）
· 引用 + 回复 + 转发同时存在
· 全部关联字段缺失（纯原创）
· 长 URL / hashtag 密集
测试流程：写完代码 → 跑 100 条样本对比旧逻辑（自动）→ 抽 20 条人工评翻译质量 → 7 种边缘 case 跑通 → 故意制造 50 次失败验证回落 → 上线观察一周看成本和用户反馈。

需要你决定的关键点

① 要不要加「完整性检查」这一步？

建议：所有步骤都跑完后，给数据盖一个时间戳。前端只展示带这个戳的推文。

好处：前端永远拿到完整数据，不用再做兜底显示。代价：新数据要等流程跑完（约 1 到 3 分钟）才上 feed。

② 已经积累的 3 万多条老数据怎么处理？

方案 A：跑一次性补全，全部走一遍新流程（估计 4 到 6 小时）
方案 B：分等级处理，最近 7 天的优先补全，更老的让兜底机制慢慢补
方案 C：老数据保留显示，但加一个「早期数据可能不完整」的标识

我倾向 B 方案 — 用户主要看最近 7 天的，先把这部分救出来，老的让兜底机制 1 周内消化。

③ 翻译失败的推文要不要展示？

方案 A：不展示，等翻译成功 — 严格但可能漏掉重要内容
方案 B：展示英文原文，旁边标「等待翻译」
方案 C：中文用户看到「翻译失败，点击跳到原推」按钮

④ 实施顺序

建议先写一份正式设计文档，跑工程评审之后再分批做。重构涉及 4 批改动：

  1. 主流程补齐第 3 / 4c / 6 / 7 步 + 第 6 步合并调用 + 提示词重写
  2. 数据失效级联（原文改了清翻译）
  3. 前端加完整性筛选
  4. 一次性补全老数据 + 兜底定时任务
✅ 已采纳：长推标记合并到第 3 步 · 判定 + 翻译合并到第 6 步 · 验收标准已列
待你拍板：①–④ 决策点 · 详情页 mockup 是否再调整
