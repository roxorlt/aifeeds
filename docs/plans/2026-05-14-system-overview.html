6 层架构

整套抓取业务可以从「数据从哪来」一路拆到「问题怎么暴露给人」，共 6 层。下图展示各层关系（实线=数据流，虚线=日志/告警链）。

关于 L3 入库层 在 L4 加工层 之前的设计原理 aifeeds 走的是 ELT（Extract-Load-Transform）而不是传统 ETL（Extract-Transform-Load）： 抓到的数据**先入库（写入原始字段 + 占位 NULL）**，然后后台 cron 异步补字段。 原因：DeepSeek 翻译 / 分类单次 4-10s，同步加工 5 分钟 cron 一定 timeout；分开后失败可重试、可分层刷新（L0-L5 只刷热门）、抓取链和加工链解耦。 所以入库时 is_relevant=NULL / content_translated=NULL / extra.gh_pending=1 都是占位，等 L4 的 cron 来补。

「记录抓了但详情页没更新」根因

架构失效层：L4 加工层。所有加工任务都是「队列驱动 + silent fail」—— 没有任何机制告诉你「某条 item 反复 enrich 失败」或「某个字段全表覆盖率掉下来了」。

失效场景触发条件覆盖情况
A · metrics 显示老数据 item 太老（L5）→ refresh-tiered 不再主动刷 仅当用户点开 drawer 才主动 refresh；feed 卡片还是老的
B · 翻译缺失 DeepSeek 持续失败 → attempts 不超 3 → 标 suspect 不抛弃 长尾失败永远缺翻译
C · quote / link_card 缺失 enriched_at 设了即跳过，syndication 不返时 silent 跳过 第一次没拿到永远拿不到（哨兵已设）
D · 长推内容被截断 detect-longform 标了 note_id 但 longform-via-sb 没消费，或 3 次重试后放弃 3 次失败后悄悄放弃

4. 首页同时拉 5 个源 items + 每个 CORS preflight

首屏发起 sources + stats + auth/me + 5 个 /api/items?source_type=...，每个跨域请求多 1 个 OPTIONS preflight：

  • 10 个 API round trip，Slow 4G 下光 preflight 吃 500-1000ms
  • 方案 A：API 合并 /api/feed/home?sources=x,gh,ph,ch,hx，一次拉所有
  • 方案 B：让 worker 走 same-origin（ai-feeds.com/api/... 反代）消除 CORS
  • 方案 C：首屏只渲染 1-2 个 tab
5. 字体 30+ 个 woff2 子集

cn-font-split 切包过细，命中过多导致首次访问大量下载。这次实测 304 缓存命中实际带宽为零，但首次访问体感慢。调粗粒度（单包 50 KB 上限）。

6. 国内 CF 节点延迟（结构性，不可消除）

ai-feeds.com 在 Cloudflare，国内访问通常走香港 / 日本节点：

  • 联通 / 移动 → 香港 50-150ms
  • 电信 → 美西 200-400ms
  • 唯一解：TODO #11 ICP 备案 + #12 .cc 国内镜像站

核心场景 walkthrough · 「英文久未翻译」

同一条 X 推文从抓回到翻译完成入 feed，两种架构走一遍：

现状（抢占式 cron）

T+0:00X 推文抓回 → 入库 D1
is_relevant=NULL, content_translated=NULL
T+0:05下个 cron tick
可能被 github-enrich 抢占
T+0:10又一个 tick
classify-pending 终于抢到 → DeepSeek 判 AI 1-2 秒
→ is_relevant=1
T+0:15下个 tick
可能被 ph-enrich 抢占
T+0:20又一个 tick
fill-translations 终于轮到 → DeepSeek 翻译 4-10 秒
T+0:21翻译入库 → 前端能看到中文
总耗时：约 21 分钟 最坏情况：1 小时+（被多个队列轮流抢占）。失败重试 3 次后 silent 抛弃 → 用户永远看英文。

迁移后（Queue + Workflow + 多 worker 并发）

T+0:00X 推文抓回 → 入库 D1
同时 enqueue classify 任务到 Queue
T+0:01classify worker 拿任务
10 个 worker 并发处理 10 条推文
DeepSeek 判 is_ai 1-2 秒
T+0:02分支判断：
• is_ai = 0 → 结束（跳过翻译）
• is_ai = 1 → enqueue translate 任务
T+0:03translate worker 拿任务
同样多 worker 并发
DeepSeek 翻译 4-10 秒
T+0:13翻译入库 → 前端看到中文
总耗时：约 13 秒（is_ai=1 路径） / 约 2 秒（is_ai=0 直接跳过翻译）
失败自动 retry + 进死信队列告警 → 不再 silent 死。
两个真正的优化（注意：classify 和 translate 必须串行，因为 translate 依赖 is_ai=1 的判定结果）： ① 入库即 enqueue —— 消除 cron 5 分钟 tick 等待。入库后立刻把 classify 任务塞进 Queue，worker 秒级拿任务。
② 每一步内部多 worker 并发 —— 同一队列多个 worker 同时拉任务（10 条推文同时被 classify 处理，不再排队）。
任务之间是依赖关系（A → B 串行），但同一类任务的多条数据可以并发。
进阶优化（可选合并）：一次 LLM 调用同时判别 + 翻译
改 DeepSeek prompt：让模型一次返 {is_ai, content_translated}。从「2 次串行 LLM 调用」变「1 次合并调用」—— 单次成本约降一半，时间从 5-12s 压到 4-8s。代价：浪费翻译 token 在 is_ai=0 的推文上（X 流大约 60% 不是 AI 相关）。
取舍：高峰期开启，平峰期关闭（按 token 成本曲线决定）。
