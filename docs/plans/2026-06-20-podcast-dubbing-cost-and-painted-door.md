> 日期:2026-06-20

### A.2 已核实单价(2026-06-20 实查,非 Gemini 估值)

**关键修正**:中文 TTS 实际计费字符 = 中文字数 × 2。108 万中文字/月 → **约 216 万计费字符/月**。

### A.3 四条方案月成本对比(当前 73 集/月、71 小时、216 万计费字符)

| 方案 | ASR | TTS(turbo) | 克隆费 | 月成本 | 说明 |
|---|---|---|---|---|---|
| **v0 全预设音色** | 121 | 432 | **0** | **≈ 555 元** | 不同说话人→不同预设音色,不串人,但不像本人 |
| v0 全预设(HD 档) | 121 | 756 | 0 | ≈ 880 元 | 同上,音质更高 |
| **混合:预设主持 + 克隆嘉宾** | 121 | 432 | **≈ 644**(73×0.89×9.9) | **≈ 1,200 元** | 嘉宾克隆是大头,但一次性嘉宾克隆价值最低 |
| 全克隆(Gemini 原案) | 121 | 432 | ≈ 2,168 | ≈ 2,720 元 | 每个说话人都克隆,克隆费爆炸 ❌ |
| **CosyVoice 2 自建(开源)** | 121* | ≈ 28(GPU) | **0**(零样本免费) | **≈ 30–150 元** | 最便宜 + 能真克隆本人,但要养 GPU + 自研流水线 |

\* 自建可换开源 Whisper,ASR 也归零。

**TTS 占 78–86%,turbo 比 HD 省约 320 元/月** —— 配音场景 turbo 音质通常够用,优先 turbo。

### A.4 主持人识别的技术风险(整套自动化最易翻车处)

说话人分离(diarization)给的是**匿名、每集独立、跨集不通用的临时编号**(说话人0/1/2),
它不知道谁是主持,编号也不稳定。要做「主持→预设、嘉宾→克隆」,必须先**可靠识别谁是主持**。

**正解:声纹比对(speaker verification)**。把嗓音特征变成数字指纹,每个节目的主持提前
登记一次,每集对各说话人算声纹、跟登记主持比距离,最近的=主持,其余=嘉宾。主持嗓音跨集稳定,匹配可靠。

**四个会翻车的点**:

| 失败模式 | 原因 | 缓解 |
|---|---|---|
| 抢话/叠音(播客最常见) | 同时说话,声音糊在一起分不开 | 只取无重叠的干净片段做比对/克隆样本 |
| 音色相近 | 俩男声→声纹接近→认反 | 设阈值 + 最优分配(各登记主持抢各自最匹配的堆) |
| 嘉宾克隆样本被污染 | 克隆要 15-30s 纯嘉宾干净音 | UVR5 去背景乐 + 挑最长单人段 |
| 冷开场/片头广告 | 「第一个说话=主持」会判错 | 声纹比对不靠出场顺序,天然规避 |

**两个工程现实**:① 火山只给「分几堆」,跨集认人大概率要自接开源声纹模型(阿里 3D-Speaker /
pyannote,本地免费);**上线前必须用几集真实播客验证火山分离质量**(抢话多+嘉宾带口音是成败关键)。
② 自动流水线必须设**信心闸门**:主持没匹配上就整集退回全预设,宁可不克隆也不能串人。

### A.5 升级阶梯(越往上越贵越复杂越易错,按需逐档加)

| 档 | 做法 | 要识别主持? | 成本 | 风险 |
|---|---|---|---|---|
| **v0 最稳** | 预设音色直接套匿名编号(说话人0→男声A) | 否 | ~555/月 | ≈0,集内绝不串人(主持中文嗓音可能每期不同) |
| **v1 品牌主持** | + 声纹比对把主持钉死在同一预设音色 | 是 | ~555/月 + 开发 | 引入 A.4 四个坑 |
| **v2 克隆嘉宾** | + 嘉宾动态克隆 | 是 + 干净样本 | ~1,200/月 | 再加克隆样本污染风险 |

### A.6 一次付费、无限播放(R2 存播)—— 这条改写整个成本结论

配音成本是**一次性、按集付**;配完把中文 MP3 存 R2,之后**不管多少人、播多少次,边际成本≈0**:
- Cloudflare R2 **出流量不收费**(招牌特性),存储仅 $0.015/GB/月;
- 一集中文 MP3 约 50MB,73 集/月新增约 3.6GB,存储费每月几毛钱;
- 基建已现成:原音已存 R2(`audio_r2_at` / `podcast_media_r2_at`),已有 `/r/<key>` 反代 +
  Range 流式播放。加中文版 = 每集多存一个 R2 对象(`extra.dub_zh_r2_key`)+ 播放器加「原音/中文」切换。

**所以 555~880 元/月是「内容生产成本」,跟受众规模完全解耦**:10 人听是这个数,10 万人听还是这个数。
听众越多摊得越薄 —— 这就是网络效应。**配几集由你决定(按需求排行榜),不是被动每月全配。**

## Part B — 假门按钮设计(先验证需求强度)

### B.1 为什么先做假门

配音方案最低也要 555 元/月持续投入 + 工程搭建。在投钱前,用**假门测试(painted door)**:
放一个「翻译成中文音频」按钮,点了不真做功能,只记录「有人想要」,用点击率量化真实需求强度。
需求强 → 按 A.5 逐档做;需求弱 → 一分钱配音费没花就否掉。

### B.2 按钮落点 + 视觉(对齐 `docs/frontend-ux-guidelines.md`)

落点:播客抽屉 `PodcastDrawerBody.tsx` 的「收听」区,**紧贴 `<audio>` 播放器下方** ——
语义是「这是英文原音,想要中文版?」最自然。

视觉:**次按钮 variant**(`border border-neutral-300`,非主 CTA,因为「听原音」才是主路径),
全宽,左侧 `IconTranslate`(lucide,零 emoji),主文案 + 一行弱化副文案。

```
收听
┌─────────────────────────────────────────────┐
│  ▶ ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━  47:02       │  原生 audio(英文原音)
└─────────────────────────────────────────────┘

┌─────────────────────────────────────────────┐
│  ⇆  翻译成中文音频                            │  次按钮:border-neutral-300
│      AI 配音 · 区分主持与嘉宾                 │  副文案 text-[11px] text-neutral-400
└─────────────────────────────────────────────┘
```

### B.3 状态机 + 点击后效果

点击后**不弹模态、不跳页**,就地把按钮换成确认态(inline),emerald 反馈色(规范:成功用 emerald):

```
点击前 ──tap──▶ 点击后(就地替换,持久化)

┌─────────────────────────────┐      ┌─────────────────────────────────────┐
│ ⇆ 翻译成中文音频             │  ──▶ │ ✓ 已加入愿望清单 · 你是第 23 个想听的 │
│   AI 配音 · 区分主持与嘉宾   │      │   做好后第一时间通知你   留邮箱通知 ▸ │
└─────────────────────────────┘      └─────────────────────────────────────┘
                                       text-emerald-600   ↑ 可选 notify,不强制
```

- 点击 = 一次「想听」票,匿名即可(见 B.4),写入 `dub_wishlist` 表去重。
- 确认态**持久化**:刷新后仍显示「✓ 已加入」(按设备查 state),让用户觉得被听见、也防重复计数。
- 「留邮箱通知」是**可选** upsell:已登录用户点一下即 `notify=1`;未登录用户轻引导到现有邮件订阅,**不强制**。

### B.4 两个关键设计决策

1. **不登录也能点(匿名)**。复用现有遥测的 `getDeviceId()`(稳定匿名设备 id)。
   若先弹登录,大量人直接走掉,测到的是「登录用户的需求」而非真实需求 —— 信号失真。
   登录用户额外带 `user_id` 做更精归因,但**绝不拿登录当点击门槛**。

2. **点击前不露计数,点击后才露**。点击前显示「N 人想听」会制造从众偏差(bandwagon),
   污染「真实想点的人有多少」这个核心信号;且冷启动「0 人想听」显得很死。
   改为**点击后**才奖励式显示「你是第 N 个想听的」—— 给点击者反馈、又不影响是否点击的决策。

## Part C — 后端数据与接口

### C.1 `dub_wishlist` 表(migration `023-dub-wishlist.sql`)

用独立表而非塞进 `events`:需要「每设备每集只算一次」的去重、需要回显「已加入」态、
需要「想通知」标记、需要干净的按集需求排行。

```sql
CREATE TABLE IF NOT EXISTS dub_wishlist (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  item_id     TEXT NOT NULL,
  device_id   TEXT NOT NULL,         -- 匿名设备 id(始终有),复用 getDeviceId()
  user_id     TEXT,                  -- 登录则带(可空)
  notify      INTEGER NOT NULL DEFAULT 0,  -- 是否想做好后通知
  created_at  INTEGER NOT NULL,      -- ms
  day         TEXT NOT NULL,         -- 北京时区 YYYY-MM-DD,做 cohort/趋势
  ip          TEXT,
  ua          TEXT,
  UNIQUE(item_id, device_id)         -- 去重:一台设备对一集只计一次
);
CREATE INDEX IF NOT EXISTS idx_dub_wishlist_item ON dub_wishlist(item_id);
CREATE INDEX IF NOT EXISTS idx_dub_wishlist_day  ON dub_wishlist(day);
```

### C.2 API 端点

| 方法 + 路径 | 鉴权 | 行为 |
|---|---|---|
| `POST /api/dub-wishlist` | 匿名(读 device_id;有 session 则带 user_id) | body `{ item_id, notify? }`;`INSERT OR IGNORE`(命中 UNIQUE 即已加入);返回 `{ ok, count, already, notify }`。`count` = 该集去重想听数(点击后才返,供「第 N 个」展示) |
| `GET /api/dub-wishlist/state?ids=a,b,c` | 匿名 | 返回这些 item 当前设备是否已加入 + 各集计数,供抽屉/feed 回显「✓ 已加入」 |

简化:抽屉打开本就调 `fetchItem(item.id)`,可直接在其响应里加 `dub_wishlisted`(本设备)
和 `dub_wishlist_count` 两个字段,省一个往返;批量 state 端点留给 feed 卡片级按钮(若后续要做)。

另外**双写一条遥测**:点击时 `track(EVENTS.DUB_WISHLIST_CLICK, { item_id })`,让它进现有 DAU/漏斗管道。

### C.3 复用现有设施(不另造轮子)

- 匿名设备 id:`dashboard/src/lib/device.ts` 的 `getDeviceId()`(遥测同款,天然去重维度)。
- 遥测:`dashboard/src/lib/telemetry.ts` 的 `track()` + `EVENTS`(加一个 `DUB_WISHLIST_CLICK`)。
- 漏斗分母:admin 已有「详情打开 · 按数据源」事件(`admin-dashboard.ts` 第 759 行),
  播客详情打开数现成,直接当「需求强度漏斗」的分母。
- Bot 过滤:复用 `admin-dashboard.ts` 的 `bot_devices` / `NOT_OWNER_SQL` CTE。

## 决策与下一步

- **配音方案**:真要做时优先 **v0 全预设 + turbo(~555 元/月)+ R2 存播**,零识别风险、成本与受众解耦;
  需求验证强且用户要「主持固定声/原声音色」再逐档上 v1/v2 或 CosyVoice 自建。
- **当前动作**:先把假门按钮 + 需求看板做了(Part B/C/D/E),用真实点击率决定后续投入。
- **未来迭代(用户已明确延后)**:ASR 转录 + DeepSeek 翻译 + 音频实时翻译。
