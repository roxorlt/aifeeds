# ScrapeBadger 抓取频率 × 月成本对照

> 用途：决定 list-poll-ingest 的 cron 调度（波峰/波谷各几分钟）时查这张表，
> 不用每次重算。算法 + 假设也写在下面便于场景变化时快速重推。
> 最后更新：2026-05-06

---

## 计费规则（已实测）

ScrapeBadger 计费按返回结果条数：

| 公式 | 说明 |
|---|---|
| `credits = 1 base + 1 × N` | N = 响应里 tweet/user 等的条数 |
| 失败请求（404/500） | 0 credits（**但仍占 rate limit 1 次**）|

实测样本：

| 请求 | N | x-credits-used |
|---|---|---|
| `tweets?tweets=A` | 1 | 2 |
| `tweets?tweets=A,B,C` | 3 | 4 |
| `tweets?tweets=A,B,C,D,E` | 5 | 6 |
| `lists/{id}/tweets`（一页）| 55 | 56 |

**单价**（PAYG）：$0.15 / 1,000 credits。
**Rate limit**（已付费）：60 req/min。

## list 端点没有 page_size 参数

每次调 `lists/{id}/tweets` 必返 ~55-56 条 → 必扣 ~57 credits。
**节流唯一杠杆是频率**（cron 间隔），单次成本不可压。

## 我们项目的固定开销

`refresh-tiered` cron 每 30 分钟一次，每 tick 拉一批已知 IDs（`get-tweets-by-ids`，1 base + N tweet），cap 在 ~21 credits/call：

- 2 ticks/小时 × 24h × 30 天 = 1,440 calls/月
- 1,440 × 21 = **30,240 credits/月 = $4.5/月**

这部分不随 list-poll 频率变化，下表里的"含 refresh"列已加。

## 算式（场景变了就重推）

```
波峰日 calls = (14 × 60) ÷ 波峰分钟数
波谷日 calls = (10 × 60) ÷ 波谷分钟数
日 calls = 波峰日 calls + 波谷日 calls
日 credits = 日 calls × 57
月 credits = 日 credits × 30
月费 = 月 credits × 0.00015
```

## 拐点 + 选档建议

| 档位 | 月费 | UX |
|---|---|---|
| 5m / 30m | **$52.7** 含 refresh | feed 实时感强（最快 5 min 见新推），性价比甜区 |
| 10m / 30m | **$31.2** 含 refresh | 比传统人工刷 X 还快一点，最高性价比 |
| 3m / 30m | **$81.5** 含 refresh | 接近 1 min 体验 / 但成本砍掉 60% |
| 1m / 30m | **$225.1** 含 refresh | $2,700/年，需要明确产品价值才上 |

**波谷 30→20→10 min** 的边际成本通常 $2-10/月，对总盘子影响小。
**波峰** 才是主成本驱动 — 5→3 min 翻倍、3→1 min 又翻 3 倍。

## 当前 prod 配置

cron mode = `list-poll-ingest` 触发于 UTC `minute === 25 || minute === 55`
→ **30 min/次（不分波峰波谷）**
→ 月成本 $12.3 + refresh $4.5 = **$16.8/月**

升级路径见上表，改的是 `worker/src/index.ts` `scheduled()` 里的
`else if (minute === 25 || minute === 55) mode = 'list-poll-ingest'`
分支条件。

实际改时按 BJT 推 UTC：
- 波峰 PT 09-23 = UTC 17-23 + 00-07 = `hour IN (17..23, 0..6)`
- 波谷 PT 23-09 = UTC 07-17 = `hour IN (7..16)`
