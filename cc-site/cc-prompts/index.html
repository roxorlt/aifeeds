52 条官方提示词中英对照，按开发阶段（发现 → 设计 → 构建 → 交付 → 运维）与角色分类，可填写占位符、一键复制。数据来自 code.claude.com 官方 Prompt library。
发现 · 入门

在新仓库中快速上手Get oriented in a new repository

❯give me an overview of this codebase: architecture, key directories, and how the pieces connect
❯给我概述一下这个代码库：架构、关键目录，以及各部分如何连接
为什么这样写有效
描述你想知道什么，而不是要读哪些文件。Claude 会自行探索项目，并返回各部分如何组合的摘要。

解释不熟悉的代码Explain unfamiliar code

❯explain what src/scheduler/queue.ts does and how data flows through it. write it up as an HTML page with a diagram, then open it in my browser
❯解释 src/scheduler/queue.ts 的作用以及数据如何流经它。以 包含图表的 HTML 页面，然后在浏览器中打开 形式输出
为什么这样写有效
指定文件并说明你想要的回答格式。可以将 HTML 页面替换为图表、要点列表或任何适合你学习方式的格式。
固化下来设置输出风格，让 Claude 始终以你偏好的格式解释

查找某件事发生的位置Find where something happens

❯where do we validate uploaded file types?
❯我们在哪里 验证上传的文件类型？
为什么这样写有效
根据行为而不是文件名搜索。即使你不知道文件叫什么或位于哪个目录，搜索也能生效。

删除前检查哪些会受影响Check what breaks before you delete

❯what would break if I deleted the retryWithBackoff helper?
❯如果我删除 retryWithBackoff 辅助函数，哪些地方会出问题？
为什么这样写有效
在移除任何内容前先询问。调用方列表和下游影响会告诉你，这只是一行代码清理，还是需要协调的变更。

追溯代码演变过程Trace how code evolved

❯look through the commit history of internal/auth/session.go and summarize how it evolved and why
❯查看 internal/auth/session.go 的提交历史，总结其演变过程及原因
为什么这样写有效
当问题是“为什么”而非“是什么”时，直接指向提交历史。Claude 会读取你使用的版本控制的日志和 blame 信息，解释当前实现背后的决策。

开始前评估变更范围Scope a change before you start

❯which files would I need to touch to add a dark mode toggle to settings?
❯我需要修改哪些文件才能 在设置中添加深色模式开关？
为什么这样写有效
在将工作纳入路线图之前，先评估工作量。文件列表会告诉你这是影响单个组件还是跨组件的变更。

向代码库提问产品问题Ask the codebase a product question

❯I am a PM. walk me through what happens when a user clicks Export to PDF, from the UI down to the result
❯我是一名 产品经理。请带我走查一下，当用户 点击导出为 PDF 时，从 UI 到结果的全过程是怎样的
为什么这样写有效
说明你的角色，这样回答会匹配正确的层次。Claude 会根据源代码解释产品实际做了什么，你无需亲自阅读代码。
固化下来设置输出风格，让 Claude 始终以此层次回答问题
设计 · 规划

在动代码之前规划多文件变更Plan a multi-file change before touching code

❯plan how to refactor the payment module to support multiple currencies. list the files you would change, but don't edit anything yet
❯规划如何重构 支付模块 以实现 支持多种货币。列出要修改的文件，但暂时不要编辑任何内容
为什么这样写有效
加上“暂时不要编辑”可以将探索与变更分开，让你在代码变动前看到方案。要在每个提示中默认采用先计划模式，可以按 Shift+Tab 进入 计划模式。

通过访谈起草规范Draft a spec by interview

❯I want to build per-workspace rate limits. interview me about implementation, UX, edge cases, and tradeoffs until we have covered everything, then write the spec to SPEC.md
❯我想构建 每个工作区的速率限制。请就实现、UX、边缘情况和权衡对我进行访谈，直到我们覆盖所有内容，然后将规范写入 SPEC.md
为什么这样写有效
要求接受访谈，而不是自己写规范。Claude 会向你提出结构化问题，直到需求完整，然后将结果写入文件。
固化下来将你的访谈问题保存为 /spec 技能，让每个规范都以相同方式开始

将会议转化为工单Turn a meeting into tickets

❯read @meeting-notes.md and write up the action items, then create a Linear ticket for each with acceptance criteria
❯阅读 @meeting-notes.md 并撰写行动项，然后为每个行动项创建一个 Linear 工单，并附上验收标准
为什么这样写有效
跳过转录步骤。Claude 通过 MCP 从非结构化输入中提取行动项，并直接写入你的追踪器，这样你只需审核工单，而非会议记录。
固化下来将此保存为 /tickets 技能

在构建之前梳理边界情况Map edge cases before building

❯list the error states, empty states, and edge cases for the file upload flow that the design needs to cover
❯列出 文件上传流程 需要覆盖的错误状态、空状态和边界情况
为什么这样写有效
询问缺失的部分，而非已有的部分。Claude 会列出快乐路径设计往往忽略的错误状态、空状态和边界情况。
设计 · 原型

将模型转化为可运行的原型Turn a mockup into a working prototype

❯here is a mockup. build a working prototype I can click through, matching the layout and states shown
❯这是一个模型。构建一个我可以点击交互的可运行原型，匹配所示的布局和状态
为什么这样写有效
可点击的原型能回答静态模型无法回答的问题。将可运行的代码交给工程团队，而无需在文档中解释交互细节。

根据截图实现并自我检查Implement from a screenshot and self-check

❯implement this design, then take a screenshot of the result, compare it to the original, and fix any differences
❯实现此设计，然后截取结果截图，将其与原图对比，并修复任何差异
为什么这样写有效
这为 Claude 提供了一个验证循环：它进行渲染，与源图像对比，然后迭代，而无需你逐一指出差距。
固化下来使用 /goal 让 Claude 持续迭代，直到截图匹配为止
构建 · 实现

遵循现有模式Follow an existing pattern

❯look at how the GitHub webhook handler is implemented to understand the pattern, then build a Stripe webhook handler the same way
❯查看 GitHub webhook 处理器 是如何实现的以理解其模式，然后以相同的方式构建 一个 Stripe webhook 处理器
为什么这样写有效
指向你认可的已有代码。如果没有参考，Claude 会默认采用通用最佳实践。有了参考，它会匹配你的代码库实际使用的约定。
固化下来要求 Claude 将所遵循的模式写入 CLAUDE.md，以便未来的会话无需参考即可匹配

为未文档化的代码生成文档Generate docs for undocumented code

❯find the public functions in src/auth/ without JSDoc comments and add them, matching the style already used in the file
❯查找 src/auth/ 中的公共函数 中缺少 JSDoc 注释的代码，并添加注释，匹配文件中已使用的风格
为什么这样写有效
指定范围和格式。Claude 会找到缺失的部分，并匹配文件中已有的注释风格，因此新文档读起来会与其余部分一致。

添加一个小而明确的功能Add a small, well-defined feature

❯add a /health endpoint that returns the app version and uptime
❯添加一个返回 应用版本和正常运行时长 的 /health 端点
为什么这样写有效
说明输入和输出，而非如何构建。Claude 会找到类似代码所在的位置，并将你的代码添加在旁边。

从零开始构建一个小的内部工具Build a small internal tool from scratch

❯create a drag-and-drop Kanban board with three columns using HTML, CSS, and vanilla JavaScript, then open it in my browser
❯使用 HTML、CSS 和原生 JavaScript 创建一个 带有三列的拖放式看板，然后在浏览器中打开它
为什么这样写有效
你不需要项目、框架或构建步骤。描述这个工具，并让 Claude 打开它，这样你就能立即看到它运行。

端到端地处理一个问题Work an issue end to end

❯read issue #312, implement the fix, and run the tests
❯阅读 issue #312，实现修复，并运行测试
为什么这样写有效
提供问题编号，而非摘要。Claude 会自行阅读完整的工单，因此你可能忘记提及的需求都会被纳入，并在报告前验证变更。

查找并更新代码库中的文案Find and update copy across the codebase

❯find every place we say "Sign up free" or a close variant, show me each one in context, then update them all to "Start free trial". leave tests and the changelog alone
❯找出所有说“免费注册”或相似措辞的地方，在上下文中显示每个，然后把它们全部更新为“开始免费试用”。测试和变更日志不要动
为什么这样写有效
要求变体并说明哪些要跳过。Claude 能找到字面搜索会遗漏的措辞，并保持测试固件和历史记录原样，这样你只审查用户真正看到的文案。

根据以往示例起草文档Draft a document from past examples

❯read the privacy impact assessments in legal/pia/ to learn the structure and voice, then draft a new one for the new analytics integration
❯阅读 legal/pia/ 里的 隐私影响评估 来学习结构和语调，然后为 新的分析集成 起草一份新的
为什么这样写有效
指向已完成工作的文件夹，而不是描述你的风格。Claude 从你已经发布的内容中学习结构和语调，这样初稿读起来就像是你的作品。
固化下来将语调保存为 skill，这样每个草稿都从这里开始

❯write tests for app/parsers/feed.py, run them, and fix any failures
❯为 app/parsers/feed.py 编写测试，运行它们，并修复任何失败
为什么这样写有效
要求一步完成编写、运行和修复，让 Claude 迭代执行，无需等待指令。
固化下来运行 /init，让 Claude 自动学习你的测试命令

根据测试驱动实现Drive implementation from tests

❯write tests for the password reset flow first, then implement it until they pass
❯先为 密码重置流程 编写测试，然后实现它直到测试通过
为什么这样写有效
测试驱动开发：测试定义了工作完成的标准，Claude 会迭代实现直到测试全部通过。

根据覆盖率报告填补空缺Fill gaps from a coverage report

❯read coverage/coverage-summary.json and add tests for the lowest-covered files until each is above 80%
❯读取 coverage/coverage-summary.json，为覆盖率最低的文件添加测试，直至每个文件高于 80%
为什么这样写有效
指向覆盖率报告，而不是猜测哪些未测试。Claude 读取实际数字，为最需要测试的文件编写测试。
固化下来将此设为 /goal，这样 Claude 会持续编写测试，直到覆盖率达到目标
构建 · 重构

跨代码库迁移模式Migrate a pattern across the codebase

❯migrate everything from the old logging API to the structured logger: identify every place that needs to change, then make the changes
❯把所有从 旧的日志 API 迁移到 结构化日志记录器：先找出每一处需要变更的地方，然后做出变更
为什么这样写有效
描述旧模式和新模式。要求 Claude 先找出所有位置，确保调用点在响应中列出，这样你能检查是否有遗漏。

将代码移植到另一种语言Port code to another language

❯port this Python module to Rust, keeping the same public API and test behavior
❯将 这个 Python 模块 移植到 Rust，保持相同的 公共 API 和测试行为
为什么这样写有效
说明要保留什么，而不仅仅是目标语言。指明必须保持不变的 API 或行为，为 Claude 提供了一个检验移植的契约。

针对可衡量的目标进行优化Optimize against a measurable target

❯optimize the search query to bring p95 latency from 2s down to under 500ms
❯优化 搜索查询，让 p95 延迟 从 2秒 降至 500毫秒 以下
为什么这样写有效
指明指标和目标，给 Claude 一个明确的完成定义。
固化下来将此设为 /goal，这样 Claude 会不断测量并迭代，直到达到该数值

修复一个精确的视觉 BugFix a precise visual bug

❯the login button extends 20px beyond the card border on mobile. fix it.
❯登录按钮 在 移动端 上超出了 卡片边框 20px，修复它。
为什么这样写有效
精确的视觉反馈能得到精确的修复。说明具体元素、尺寸和视口。
固化下来添加一个预览工具，这样 Claude 可以自行截图并验证修复
构建 · 审查

提交前检查你的更改Review your changes before you commit

❯review my uncommitted changes and flag anything that looks risky before I commit
❯在提交前，检查我未提交的更改，并将任何看起来有风险的地方标记出来
为什么这样写有效
在修复成本还很低时尽早发现问题。Claude 会完整读取已更改的文件，而不仅仅是差异行，因此能发现快速自查时遗漏的问题。
固化下来用一条命令运行 /code-review 执行相同的检查

审查一个拉取请求Review a pull request

❯review PR #247 and summarize what changed, then list any concerns
❯审查 PR #247，总结变更内容，然后列出所有问题
为什么这样写有效
Claude 在上下文中结合整个代码库进行审查，而不仅仅是差异内容。它会读取变更的代码及其调用的部分，因此能捕获仅查看差异的审查所遗漏的问题。
固化下来使用 Code Review 对每个 PR 启用此功能

在应用前审查基础设施变更Review infrastructure changes before applying

❯here is my Terraform plan output. what is this going to do, and is anything here going to cause problems?
❯这是我的 Terraform plan 输出。这将会执行什么操作？其中是否存在会导致问题的内容？
为什么这样写有效
Plan 输出内容密集且难以浏览。粘贴它后，在应用之前，你能获得一个用通俗语言总结的实际将要变更的内容。

使用子代理运行安全审查Run a security review with a subagent

❯use a subagent to review src/api/ for security issues and report what it finds
❯使用一个子代理审查 src/api/ 中的安全问题，并报告发现的问题
为什么这样写有效
一个子代理会在自己的上下文窗口中运行审计，并返回摘要，因此长时间的安全审查不会填满你的主会话。内置的通用子代理无需额外设置即可处理此任务。
固化下来设置一个你的整个团队都可以使用的专用安全审查子代理

在正式审查之前发现问题Catch issues before formal review

❯review launch-post.md for unsupported claims, missing attributions, and brand-guideline issues and list anything I should fix before it goes to legal
❯审查 launch-post.md 中是否存在 无根据的声明、缺失的署名以及品牌指南问题，并列出在发送给 法务 之前我应该修复的所有内容
为什么这样写有效
在人工投入时间之前，先进行一次初步审查。明确指出你想检查的问题，让审查更有针对性，然后修复发现的问题，发送更干净的草稿。
固化下来将你的审查检查清单捕获为团队可运行的技能
构建 · 引导

纠正错误的方法Course-correct a wrong approach

❯that is not right: the function signature needs to stay backward-compatible. try a different approach
❯那不正确：函数签名需要保持向后兼容。尝试一种不同的方法
为什么这样写有效
指出 Claude 遗漏的具体约束，而不仅仅是说它错了。一个具体的理由能为 Claude 提供重试时需满足的明确约束，而不是再次猜测。
固化下来按两下 Esc 打开回退菜单并恢复代码和对话，使重试从一个干净的状态开始

缩小变更范围Narrow the scope of a change

❯that is too much. keep only the changes to the validation logic in src/forms/ and undo your other edits
❯这范围太大了。仅保留对 src/forms/ 中的校验逻辑 所做的更改，并撤销你的其他编辑
为什么这样写有效
当方向正确但变更范围过大时，让 Claude 保留其中一部分，而不是全部回退。明确边界可以防止小修复演变成重构。

将一条纠正转化为规则Turn a correction into a rule

❯you keep using default exports when this project uses named exports. add a rule to CLAUDE.md so this stops happening
❯你总是 在本项目使用命名导出时却使用了默认导出。在 CLAUDE.md 中添加一条规则，以避免这种情况再次发生
为什么这样写有效
聊天中的纠正不会与你的团队共享。项目 CLAUDE.md 中的规则一旦提交即被共享，Claude 会在每个会话开始时读取它。
固化下来打开 /memory 查看 Claude 写的内容
